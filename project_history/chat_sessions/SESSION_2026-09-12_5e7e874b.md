### Why Waypoints MUST Be Defined on the Map

1. **Waypoints are Static World Locations:**  
   When we dispatch:
   ```python
   pose.header.frame_id = 'map'
   pose.pose.position.x = 0.40  # 40 cm along corridor in the room
   pose.pose.position.y = 0.00
   ```
   This is a permanent address in the room. Even if you pick the robot up or turn off the sensors, $(0.40, 0.00)$ on the map stays in the exact same spot on the floor.

2. **LiDAR Scans Are "Ego-Centric" (Robot-Relative):**  
   The LiDAR scanner measures raw distances relative to *itself* (`laser_frame`).
   * If a wall is $2.0\,\text{m}$ in front of the robot, the LiDAR reports: `"Obstacle at +2.0m"`.
   * When the robot drives $1.0\,\text{m}$ forward, the LiDAR now reports: `"Obstacle at +1.0m"`.  
   Because LiDAR measurements shift every millisecond as the robot moves, **you cannot set waypoints in the LiDAR frame**, or the waypoints would move with the robot like a carrot dangling on a stick!

### How They Connect Together (The Coordinate Chain)

ROS 2 uses **REP-105 coordinate transforms** to link the moving LiDAR scans to the fixed map waypoints:

```
[ MAP Frame ]  <─── Waypoints (H, 1, 2, 3) are fixed here
      ▲
      │  (AMCL scan-matching compares LiDAR beams to static walls)
      │
[ ODOM Frame ] (Wheel encoders + Gyro continuous dead-reckoning)
      ▲
      │
[ BASE_FOOTPRINT ] (Moving Robot Chassis)
      ▲
      │
[ LASER_FRAME ] <─── Raw red LiDAR scan points are measured here
```

1. The robot reads raw red laser beams in its own local frame (`laser_frame`).
2. **AMCL** compares those red laser beams to the black walls on the blueprint (`map`).
3. Once AMCL aligns the red dots onto the black walls, it knows the robot's exact position on the blueprint.
4. Nav2 then draws a path from the robot's current position to the **fixed waypoint on the map**!

### 2. Why did the map appear static?

We identified the root cause in the visualizer architecture:

1. **The 500 ms Browser Request Abortion Loop:**
   * On the backend, rendering the 3.5× scaled map, path layers, badges, and encoding JPEG synchronously on the Raspberry Pi 5 CPU took **$530\,\text{ms} - 720\,\text{ms}$**.
   * In the browser frontend, JavaScript used a rigid timer: `setInterval(refreshImage, 500)`.
   * In modern web browsers (Chromium/Firefox), if you assign a new `img.src` before the previous image download has completed, the browser **immediately aborts the in-flight request** (`net::ERR_ABORTED`).
   * Because every image request took $>500\,\text{ms}$, **every single frame download was cancelled before the browser could decode it**! The browser was trapped in a continuous cancellation loop, perpetually displaying the initial frame from when the tab was opened.
